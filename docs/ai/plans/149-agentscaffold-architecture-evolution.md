## 1. Objective

Evolve AgentScaffold from a static instruction generator into a runtime-composable agent
framework by implementing the five initiatives identified in the architecture study, with
Cursor as the primary target platform and Claude Code as the migration destination:

1. **GraphBackend protocol + DuckDB migration** -- Eliminate the dead KuzuDB dependency
   by abstracting the graph layer and migrating to DuckDB + DuckPGQ.
2. **Hook generation system** -- Enable real-time governance enforcement by generating
   platform-native lifecycle hooks from a single intent-based configuration.
3. **Agent definitions + ReviewFinding write-back** -- Transform expert reviewers into
   spawnable agents that read from and write back to the knowledge graph.
4. **Skills standard adoption** -- Publish domain knowledge as SKILL.md files for
   cross-platform discovery.
5. **Plugin packaging** -- Make domain packs distributable as standalone packages.
6. **Eval harness expansion** -- Extend the evaluation harness to cover all new
   capabilities: backend parity, finding lifecycle, artifact generation correctness,
   new tool adoption routing, and review-enrichment efficiency.

Success means:
- `scaffold index` runs on DuckDB by default with query parity verified against KuzuDB
- `scaffold agents generate --all-platforms` produces hooks, agents, skills, and rules
  for Claude Code, Cursor, and Windsurf from a single `scaffold.yaml`
- `scaffold_record_finding` and `scaffold_resolve_finding` MCP tools exist and write to
  the graph in real-time
- All existing tests pass against both KuzuDB and DuckDB backends
- No platform-specific intelligence in generated artifacts (MCP-first principle)
- `scaffold agents cursor` generates per-reviewer agent-requested rule files
  (`.cursor/rules/<reviewer>.md`) with YAML frontmatter for each configured domain
  reviewer, giving Cursor the functional equivalent of Claude Code spawnable subagents
- All Cursor-generated rule files use typed frontmatter (`alwaysApply` / glob-attached /
  agent-requested) instead of flat markdown, enabling proper rule scoping
- `.cursor/mcp.json` is generated by `scaffold agents cursor` and `--all-platforms`,
  eliminating the primary manual setup step for the primary platform
- Domain pack manifests support `file_patterns:` so Cursor rules auto-attach to
  relevant file patterns rather than loading globally
- `scaffold agents windsurf` generates Windsurf Cascade-compatible agent definition
  stubs alongside `.windsurfrules`
- Eval harness scenario count grows from ~79 to ~109, covering both backends, all new
  MCP tools, artifact generation correctness, finding lifecycle, and new adoption routes

## 2. Non-Goals

- Building an AgentScaffold hook runtime (hooks are generated for platforms, not executed
  by AgentScaffold at CLI time beyond its own internal dispatch)
- LSP integration (deferred; the graph already provides this capability)
- Marketplace or registry for plugins (pip distribution only)
- Real-time collaboration features (multi-agent concurrent graph writes)
- Migrating gitnexus or any other package in this monorepo
- Supporting graph backends other than KuzuDB and DuckDB+DuckPGQ
- Cline, Continue, aider, or Codex platform-specific artifacts (these platforms reuse
  AGENTS.md and MCP natively; no generated artifacts are needed)

## 3. Constraints / Invariants
- Must not break: Existing `scaffold index`, `scaffold mcp`, `scaffold agents` CLI behavior
- Must not break: Existing test suite (all 20 test files must pass throughout)
- Backward compatibility: KuzuBackend must remain functional as a fallback after migration
- Backward compatibility: `scaffold.yaml` must remain backward-compatible (new sections are additive)
- Backward compatibility: Domain pack manifests without `file_patterns:` must continue to
  work; absence of the field defaults to `alwaysApply: true` for all generated Cursor rules
- Performance constraints: `scaffold_record_finding` MCP tool must respond in <200ms
- Performance constraints: DuckDB backend must match or exceed KuzuDB query latency for all 111 queries
- Data integrity constraints: Graph data must survive backend switch with zero data loss
- Breaking change: No (additive changes only; KuzuBackend preserved)

## 4. Current State

AgentScaffold is a Python CLI tool (``) that:

- **Indexes codebases** via `scaffold index` into a KuzuDB knowledge graph (17 files in
  `graph/` module: schema, store, parsing, imports, calls, structure, governance,
  communities, embeddings, sessions, incremental, pipeline, verify, search, queries,
  symbol_table)
- **Exposes graph intelligence** via `scaffold mcp` as an MCP server with 18+ tools
  (3 files in `mcp/` module: server, freshness, __init__)
- **Generates agent instructions** via `scaffold agents` for Claude Code, Cursor,
  Windsurf (7 files in `agents/` module: generate, prompt, claude, cursor, windsurf,
  rule_policy)
- **Runs reviews** via `scaffold review` with expert personas (7 files in `review/`
  module: verify, brief, feedback, queries, challenges, gaps)
- **Has async freshness** via background incremental indexing with debounce and
  single-flight locking

Key limitations:
1. KuzuDB was archived October 2025 -- continuing to build on it is unsustainable
2. All 111 Cypher queries are hardcoded against KuzuDB's API
3. Agent generation produces static instruction documents, not runtime-dispatchable agents
4. No lifecycle hooks for real-time governance enforcement
5. ReviewFinding nodes exist in the schema but have no MCP write path
6. No SKILL.md generation; domain knowledge locked in Jinja2 templates
7. Domain packs are not distributable outside the monorepo
8. Cursor rule files are flat markdown with no YAML frontmatter; all rules load with
   equal priority regardless of context, wasting context budget and defeating scoped
   enforcement
9. `.cursor/mcp.json` must be manually configured; there is no generated setup
10. Domain reviewer personas have no Cursor-native representation; they exist only as
    inline prompt injections, never as self-selecting rule files
11. Windsurf agent generation is instructional-only with no Cascade agent stubs

## 5. Target State

After implementation:

```
Platform layer:  HOW to invoke  (hooks, agents, rules -- platform-specific, generated)
                      |
                      v calls
MCP layer:       WHAT to invoke  (scaffold tools -- platform-agnostic, universal)
                      |
                      v queries
Graph layer:     WHAT is known   (DuckDB + DuckPGQ -- stable, maintained, vector search)
```

- **Graph**: Runs on DuckDB + DuckPGQ by default; KuzuBackend available as fallback;
  GraphBackend protocol makes backends interchangeable
- **MCP**: Two new write-path tools (`scaffold_record_finding`, `scaffold_resolve_finding`)
  close the read-write memory loop; `scaffold_prepare_review` output includes reviewer
  hint metadata (which rule files to activate in Cursor)
- **Hooks**: `scaffold agents hooks` generates `.claude/settings.json` hooks (deterministic,
  blocking) and `.cursor/rules/` files (typed frontmatter, scoped enforcement) and
  `.windsurfrules` from a single `scaffold.yaml` enforcement config
- **Agents**: `scaffold agents claude-agents` generates `.claude/agents/*.md` (Claude Code
  spawnable subagents); `scaffold agents cursor` generates `.cursor/rules/<reviewer>.md`
  (Cursor agent-requested rules, equivalent function); `scaffold agents windsurf` generates
  `.windsurf/agents/<reviewer>.md` (Windsurf Cascade stubs)
- **Cursor rule taxonomy**: Three rule classes with typed frontmatter --
  governance/prohibitions/MCP routing → `alwaysApply: true`; domain standards →
  glob-attached via `globs:` from domain pack `file_patterns:`; expert reviewer content →
  `alwaysApply: false` with rich `description:` for agent-requested activation
- **Skills**: `scaffold agents skills` generates `SKILL.md` files from domain standards
- **Config**: `scaffold.yaml` gains `enforcement:`, `reviews:`, `platforms:` sections
  expressing platform-agnostic intent; domain pack `manifest.yaml` gains optional
  `file_patterns:` for scoped glob-attachment
- **Plugin**: Domain packs have `plugin.json` manifest and are installable via pip

## Appendix A: Retrospective

**Date**: 2026-03-16
**Completed by**: AI Agent + daverobb

### What Went Well

**GraphBackend protocol design held up.** The structural Protocol abstraction made the
DuckPGQ migration surgical. Every consumer was already calling `store.query()` through
a thin interface, so the backend swap required no changes to business logic — only to
the `_open_store_for_pipeline()` dispatch function. The audit step (A.0) that catalogued
all 17 consumers before starting paid off directly.

**DuckPGQ spike was the right gate.** The 1-hour spike (A.0.5) on the 5 most complex
queries surfaced the critical `GRAPH_TABLE` variable scoping constraint before any query
translation work started. Discovering it upfront meant `query_compat.py` was designed
with the right abstraction from the beginning rather than retrofitting it later.

**Eval harness expansion tracked implementation progress.** Writing the eval scenarios
in parallel with the implementation (rather than after) gave early signal on broken
behaviour. The `test_adoption.py` suite caught the `scaffold_prepare_review` / 
`scaffold_record_finding` routing conflict before any manual testing was done.

**Normalizer-based routing fixes were surgical.** The 3 paraphrase misses were resolved
with 3 three-line normalizer entries rather than reworking the entire intent classifier.
The pattern (canonicalise ambiguous phrases before scoring) generalises well.

### What Was Harder Than Expected

**Pre-commit ruff-format inconsistency** caused repeated stash conflicts. The pre-commit
hook uses the repo-root `pyproject.toml` ruff config, but `ruff format` run from
`` picks up the package's own config. Formatting diverged on
every commit until the workflow was established: always run `python -m ruff format` from
the **repo root** before staging. This should be documented in CONTRIBUTING.md.

**Query translation scope grew mid-phase.** Phase A assumed ~20 queries needed
translation; the actual audit counted 111. The risk register captured this, and strict
per-module ordering kept scope controlled, but the volume meant A.7 (translation) was
the longest single step. A more granular audit in A.0 (counting queries per module)
would have produced a better time estimate.

**Lifecycle test backend parametrisation** required a separate temp directory for the
KuzuDB fixture (`sim_project_path_kuzu`) because KuzuDB and DuckDB can't share a db
file path. This was a conftest coupling issue that took two iterations to resolve cleanly.

### Findings

**B-149-1 (Low): README reframe deferred**
The E.9b README value proposition reframe was deprioritised because the full eval run
(all 115 scenarios) requires live graph infrastructure that wasn't available in the
implementation sessions. The reframe intent is documented and the copy update is a
straightforward task once the harness runs end-to-end with real metrics.

**B-149-2 (Medium): DuckDB concurrent write hardening not complete**
The `scaffold_record_finding` solo write latency is < 200ms (eval confirmed). However,
the async freshness coordinator (Plan 148) can hold a DuckDB WAL lock concurrently.
A concurrent-write latency test was identified in the risk register but not implemented
in Phase E. Under high MCP call frequency, latency may exceed the target.
**Action**: Add a concurrent write test in a follow-up hardening pass. Consider a write
serialization lock shared between the freshness coordinator and MCP write tools.

**B-149-3 (Low): `query_compat.ql()` dual-dialect maintenance burden**
Every new query that touches multi-hop edges must be written twice (Cypher + SQL/PGQ).
This is manageable today but will become a friction point as query complexity grows.
A longer-term option is a thin query compiler that emits both dialects from a single
AST — but this is premature until the KuzuDB backend is formally deprecated.

### Learnings

- **Spike before protocol design, not after.** Even for "low-risk" migrations, a
  time-boxed spike that runs the hardest queries validates the feasibility assumption
  that the entire architecture depends on.
- **Keep eval and implementation in the same phase.** E-phase scenarios written
  alongside C/D implementation caught bugs within the same session rather than
  in a separate QA pass.
- **Document ruff config precedence in dev setup.** Any monorepo with nested
  `pyproject.toml` files and pre-commit hooks has this footgun. One sentence in the
  setup guide would have saved multiple commit attempts.
