## 1. Bug Description

Four follow-up items surfaced after Plan 212 closed the graph-integrity and rendering
work. Together they prevent the knowledge graph from accumulating value during normal use
("graph as memory") and leave two correctness/perf gaps in the incremental indexer.

1. **Finding-capture loop is open (Item 1).** `_tool_begin_plan` and `_tool_complete_plan`
   already auto-write challenges/gaps/retro insights as `ReviewFinding` nodes, but they do
   NOT pass `file_paths`, so no `FINDING_ABOUT_FILE` edges are created. The `[PATTERN]`
   recurring-finding detector in `challenges.py::_check_patterns` traverses
   `(ReviewFinding)-[FINDING_ABOUT_FILE]->(File)` -- with no such edges it can never fire,
   so findings never compound into reviewer memory.

2. **Incremental governance freshness (Item 2).** `_run_incremental` refreshes governance
   only when the code changeset is non-empty, and `compute_changeset` filters disk files by
   indexed languages -- so a plan/learning/contract markdown edit with no code change never
   triggers a governance refresh; the new content is invisible until a full `scaffold
   index`. Conversely, every code edit pays a ~2.7s full governance clear-and-reingest even
   when no governance doc changed. Both stem from governance refresh being keyed off the
   code changeset rather than the governance documents themselves.

3. **Hook installation unverified (Item 3).** The 750x edge-duplication disaster (Plan 212)
   originated from a `PostToolUse` hook running the buggy incremental path. The bug is
   fixed, but we have not confirmed the hook is actually installed in this repo and behaves
   (stable edge counts across repeated real edits).

4. **Embeddings opt-in + per-file scoping (Item 4).** Embeddings are generated only when
   `--embeddings` is passed; an interrupted index leaves `EmbeddingStore` empty. Decide
   whether to honor a config flag so embeddings are generated by default. Assess (do not
   necessarily implement) per-file scoping of incremental re-resolution.

## 2. Root Cause

### Item 1: findings written without file links
`server.py::_tool_begin_plan` maps challenges/gaps to finding dicts with only
`category`/`finding`/`severity`; `record_findings_batch` creates `FINDING_ABOUT_FILE`
edges only when an item carries `file_paths`. The challenge/gap `evidence` dicts contain
the relevant file paths but are discarded.

### Item 2: governance refresh keyed off code changeset
`_run_incremental` early-returns when `added/modified/deleted` are all empty (doc-only
edits produce no code changeset because `compute_changeset` filters by indexed language),
and when it does proceed it always runs `clear_governance()` + `process_governance()`
(~2.7s measured) regardless of whether any governance document changed.

### Item 3 / Item 4: verification + configuration
No automated assertion that the hook is installed; embeddings generation is gated on a CLI
flag with no config default.

## 10. Retrospective

**Execution date**: 2026-06-12. **Effort**: about as expected; most of the time went to
understanding the existing incremental/governance flow rather than writing code.

The investigation phase paid off: three of the four items turned out smaller than the
headline suggested. Item 1's write-back machinery already existed in `begin_plan`/
`complete_plan` -- the only real gap was that findings were written without `file_paths`,
so the fix was a path-extractor plus threading `evidence` through `prepare_review`. Item 4's
config flag (`graph.embeddings`) already existed; only the CLI wiring to honor it was
missing. Item 3 was pure verification and surfaced the most useful non-code finding: the
incremental hook is installed in the Claude Code app but Cursor has no equivalent, so graph
auto-refresh does not happen while working in Cursor.

The most valuable code change was Item 2's governance fingerprint gate. It is both a
correctness fix (doc-only edits now refresh governance, which they never did) and a
performance fix (code-only edits skip the measured ~2.7s governance reingest that the
PostToolUse hook was paying on every single edit). Measuring that 2.7s cost before deciding
the approach was what tipped the design from "always refresh" to a fingerprint sidecar.

Verifying `clear_governance`'s preservation set (ReviewFinding + FINDING_ABOUT_FILE/FUNC
survive) before relying on it was essential -- it is what makes both the finding file-links
(Item 1) and runtime findings durable across the now-more-frequent governance refreshes.

**Deferred (documented, not silent):** per-file scoping of import/call re-resolution
(Item 4.3) and Cursor hook installation (Item 3 remediation, a human decision).

**One-sentence summary**: Closed the finding-capture loop (file-linked findings enable the
PATTERN detector), made incremental governance refresh correct-and-cheap via a fingerprint
gate, honored the embeddings config default, and confirmed the incremental hook is installed
in Claude Code (absent in Cursor). **Confidence: 5/5.**
